Views و Indexes

هتتعلم إزاي تنظم الـ Queries بتاعتك في Views وتسرّع أداء الداتابيز بالـ Indexes - من أهم المواضيع في الشغل الحقيقي!

المقدمة

ليه محتاج Views و Indexes؟

تخيل إنك بتكتب نفس الـ Query المعقدة كل يوم 10 مرات... أو إن query بسيطة بتاخد 30 ثانية على جدول فيه مليون صف. هنا بالظبط بتيجي أهمية Views و Indexes!

👁️

Views

بتحفظ الـ Queries المعقدة وتخليها سهلة الاستخدام - زي الـ shortcut!

⚡

Indexes

بتسرّع البحث في البيانات بشكل رهيب - الفرق ممكن يكون من 30 ثانية لـ milliseconds!

🔒

Security

Views بتساعدك تتحكم في البيانات اللي كل مستخدم يقدر يشوفها

الجزء الأول - VIEWS

إيه هي الـ View؟

🪟

تشبيه بسيط: الـ View = شباك!

تخيل إن عندك مخزن كبير فيه بضاعة كتير (الـ Table). الـ View هي شباك بتبص منه على جزء معين من المخزن. البضاعة هي هي، بس أنت بتشوف جزء محدد منها بالطريقة اللي أنت عايزها.

تعريف تقني:

الـ View هي جدول افتراضي (Virtual Table) مبنية على SELECT query. مش بتخزن بيانات فعلية، لكن بتخزن الـ Query نفسها وبتنفذها كل ما حد يستدعيها.

💡 نقطة مهمة: الـ View مش بتنسخ البيانات! لو البيانات الأصلية اتغيرت في الجدول، الـ View هتعرضها متحدثة تلقائياً.
إنشاء

إنشاء أول View

الصيغة الأساسية

SQL - CREATE VIEW Syntax 
CREATE VIEW view_name AS
SELECT column1, column2, ...
FROM table_name
WHERE condition;

مثال عملي: View للموظفين النشطين

عندنا جدول employees فيه كل الموظفين. عايزين View بتعرض بس الموظفين اللي شغالين:

SQL - أول View 
-- إنشاء View للموظفين النشطين
CREATE VIEW active_employees AS
SELECT employee_id, first_name, last_name, salary, department_id
FROM employees
WHERE status = 'ACTIVE';

-- دلوقتي تقدر تستخدمها زي أي جدول عادي!
SELECT * FROM active_employees;

-- تقدر تعمل WHERE عليها كمان
SELECT first_name, salary
FROM active_employees
WHERE salary > 5000;

View مع حساب (Computed Column)

SQL - View مع عمود محسوب 
CREATE VIEW employee_summary AS
SELECT
    employee_id,
    first_name || ' ' || last_name AS full_name,
    salary,
    salary * 12 AS annual_salary,
    hire_date,
    ROUND(MONTHS_BETWEEN(SYSDATE, hire_date) / 12) AS years_worked
FROM employees
WHERE status = 'ACTIVE';
✅ كده بدل ما تكتب الحسابات دي كل مرة: بس اكتب SELECT * FROM employee_summary وخلاص!
متقدم

View مع JOINs

هنا بتبان القوة الحقيقية للـ Views! لما عندك Query فيها JOINs معقدة، بتحولها لـ View وبتستخدمها بسهولة:

SQL - View مع JOIN 
-- View بتجمع بيانات الموظف مع القسم والمدير
CREATE VIEW employee_details AS
SELECT
    e.employee_id,
    e.first_name || ' ' || e.last_name AS employee_name,
    e.salary,
    d.department_name,
    m.first_name || ' ' || m.last_name AS manager_name
FROM employees e
JOIN departments d ON e.department_id = d.department_id
LEFT JOIN employees m ON e.manager_id = m.employee_id;

-- دلوقتي استخدمها ببساطة!
SELECT employee_name, department_name, manager_name
FROM employee_details
WHERE department_name = 'IT';
SQL - View مع GROUP BY 
-- View لإحصائيات كل قسم
CREATE VIEW department_stats AS
SELECT
    d.department_name,
    COUNT(e.employee_id) AS total_employees,
    ROUND(AVG(e.salary)) AS avg_salary,
    MAX(e.salary) AS max_salary,
    MIN(e.salary) AS min_salary,
    SUM(e.salary) AS total_salaries
FROM departments d
LEFT JOIN employees e ON d.department_id = e.department_id
GROUP BY d.department_name;

-- عايز تعرف أكتر قسم رواتب؟
SELECT * FROM department_stats
ORDER BY total_salaries DESC;
تعديل

تعديل وحذف View

CREATE OR REPLACE VIEW

لو عايز تعدل View موجودة، استخدم CREATE OR REPLACE:

SQL - تعديل View 
-- تعديل View موجودة (لو مش موجودة هيعملها جديدة)
CREATE OR REPLACE VIEW active_employees AS
SELECT employee_id, first_name, last_name, salary, department_id, hire_date
FROM employees
WHERE status = 'ACTIVE'
  AND hire_date >= ADD_MONTHS(SYSDATE, -12); -- الموظفين الجدد بس

حذف View

SQL - DROP VIEW 
-- حذف View
DROP VIEW active_employees;

-- الأمان: لو مش موجودة مش هيطلع error
-- (في بعض versions مش بتدعمها)
⚠️ حذف View مش بيأثر على البيانات! الـ View بس واجهة. لما تحذفها، البيانات في الجداول الأصلية بتفضل زي ما هي.
أمان

WITH CHECK OPTION

لو الـ View بتاعتك updatable (تقدر تعمل INSERT/UPDATE من خلالها)، ممكن حد يدخل بيانات ما تظهرش في الـ View! الحل هو WITH CHECK OPTION:

SQL - WITH CHECK OPTION 
-- View للموظفين اللي مرتبهم أكتر من 3000
CREATE VIEW high_salary_emp AS
SELECT employee_id, first_name, salary
FROM employees
WHERE salary > 3000
WITH CHECK OPTION;

-- ده هينجح ✅
UPDATE high_salary_emp
SET salary = 5000
WHERE employee_id = 101;

-- ده هيفشل ❌ (لأن 2000 < 3000 فمش هيظهر في الـ View)
UPDATE high_salary_emp
SET salary = 2000
WHERE employee_id = 101;
-- ORA-01402: view WITH CHECK OPTION where-clause violation
💡 الخلاصة: WITH CHECK OPTION بتمنع أي INSERT أو UPDATE يخلي الصف يختفي من الـ View.
حماية

READ ONLY View

لو عايز الـ View تكون للقراءة بس ومحدش يقدر يعمل فيها INSERT أو UPDATE أو DELETE:

SQL - READ ONLY View 
CREATE VIEW salary_report AS
SELECT
    d.department_name,
    COUNT(*) AS emp_count,
    SUM(e.salary) AS total_salary
FROM departments d
JOIN employees e ON d.department_id = e.department_id
GROUP BY d.department_name
WITH READ ONLY;

-- أي محاولة تعديل هتفشل ❌
-- ORA-42399: cannot perform a DML operation on a read-only view

الجزء الثاني - INDEXES

إيه هو الـ Index؟

📖

تشبيه: فهرس الكتاب!

تخيل كتاب فيه 1000 صفحة وعايز تلاقي كلمة "Oracle". من غير فهرس، لازم تقلب كل الصفحات واحدة واحدة (Full Table Scan). لكن لو في فهرس في آخر الكتاب، بتروح على الحرف O وتلاقي رقم الصفحة على طول!

تعريف تقني:

الـ Index هو data structure (عادةً B-Tree) بيخزن قيم عمود معين مرتبة، مع pointer لمكان الصف الفعلي في الجدول. بيخلي البحث أسرع بكتير!

الفرق بوضوح:

بدون Index
Full Table Scan - 30 sec
مع Index
0.01s
✅ نقطة مهمة: Oracle بيعمل Index تلقائياً على الـ PRIMARY KEY وعلى أي عمود عليه UNIQUE constraint. يعني الـ employee_id عليه Index من الأول!
إنشاء

إنشاء Index

الصيغة الأساسية

SQL - CREATE INDEX Syntax 
CREATE INDEX index_name
ON table_name (column_name);

أمثلة عملية

SQL - إنشاء Indexes 
-- Index على اسم الموظف (لو بتبحث بالاسم كتير)
CREATE INDEX idx_emp_lastname
ON employees (last_name);

-- دلوقتي البحث بالاسم هيكون سريع جداً!
SELECT * FROM employees
WHERE last_name = 'Ahmed'; -- ⚡ Index Scan بدل Full Table Scan

-- Index على الـ department_id (لتسريع الـ JOINs)
CREATE INDEX idx_emp_dept
ON employees (department_id);

-- Index على الـ email (لو بتبحث بالإيميل)
CREATE INDEX idx_emp_email
ON employees (email);
💡 تسمية الـ Indexes: العادة إنك تبدأ الاسم بـ idx_ بعدين اسم الجدول بعدين اسم العمود. مثلاً: idx_employees_lastname أو المختصر idx_emp_lastname
أنواع

أنواع الـ Indexes

🌳

B-Tree Index

الـ Default والأكثر استخداماً. ممتاز للقيم الفريدة والمتنوعة مثل الأسماء والأرقام

🗺️

Bitmap Index

للأعمدة اللي فيها قيم قليلة ومتكررة مثل الجنس (M/F) أو الحالة (Active/Inactive)

🔑

Unique Index

بيضمن إن كل قيمة تكون فريدة. Oracle بيعمله تلقائي على PRIMARY KEY

🔗

Composite Index

Index على أكتر من عمود. مفيد لما بتبحث بأكتر من شرط مع بعض

SQL - أنواع Indexes 
-- B-Tree Index (الـ Default)
CREATE INDEX idx_emp_salary
ON employees (salary);

-- Unique Index (ما ينفعش يتكرر)
CREATE UNIQUE INDEX idx_emp_email_unique
ON employees (email);

-- Bitmap Index (للقيم المتكررة)
CREATE BITMAP INDEX idx_emp_status
ON employees (status);

-- Function-Based Index (للبحث case-insensitive)
CREATE INDEX idx_emp_upper_name
ON employees (UPPER(last_name));
⚠️ ملاحظة عن Function-Based Index: لما تعمل Index على UPPER(last_name)، الـ Index هيشتغل بس لما تستخدم WHERE UPPER(last_name) = 'AHMED' في الـ Query. لازم الـ function تكون نفسها!
متقدم

Composite Index (Index على أكتر من عمود)

SQL - Composite Index 
-- Index على department_id و salary مع بعض
CREATE INDEX idx_emp_dept_salary
ON employees (department_id, salary);

-- ده هيسرّع الـ queries دي:

-- ✅ هيستخدم الـ Index (العمود الأول موجود)
SELECT * FROM employees
WHERE department_id = 10;

-- ✅ هيستخدم الـ Index (العمودين موجودين)
SELECT * FROM employees
WHERE department_id = 10 AND salary > 5000;

-- ❌ مش هيستخدم الـ Index! (العمود الأول مش موجود)
SELECT * FROM employees
WHERE salary > 5000;
💡 قاعدة مهمة (Leading Column Rule): في الـ Composite Index، الترتيب مهم! الـ Index بيشتغل بس لما العمود الأول (أو الأول + التاني...) موجود في الـ WHERE. فكّر فيها زي دليل التليفون: لازم تعرف الحرف الأول عشان تلاقي الاسم!
أفضل ممارسات

امتى تستخدم Index؟

✅ استخدم Index في الحالات دي:

الحالة السبب مثال
أعمدة الـ WHERE الشائعة بتبحث فيها كتير WHERE email = ...
أعمدة الـ JOIN بتسرّع ربط الجداول ON e.dept_id = d.id
أعمدة الـ ORDER BY بتسرّع الترتيب ORDER BY hire_date
الجداول الكبيرة الفرق يكون واضح أكتر من 10,000 صف
القيم الفريدة أو شبه فريدة B-Tree ممتاز هنا email, phone, SSN
تحذيرات

امتى تتجنب Index؟

❌ متعملش Index في الحالات دي:

الحالة السبب
جداول صغيرة (أقل من 1000 صف) Full Table Scan ممكن يكون أسرع!
أعمدة بيتعمل عليها INSERT/UPDATE كتير كل عملية كتابة لازم تحدّث الـ Index كمان
أعمدة فيها NULL كتير B-Tree مش بيخزن NULL
أعمدة قيمها قليلة ومتكررة مثلاً عمود gender فيه بس M/F (استخدم Bitmap بدل B-Tree)
🚨 تحذير مهم: الـ Index بيحتل مساحة تخزين وبيبطّئ عمليات الكتابة (INSERT, UPDATE, DELETE). كل ما تكتب صف جديد، Oracle لازم يحدّث كل الـ Indexes اللي على الجدول. فمتكترش من الـ Indexes من غير سبب!
⚖️

Trade-off: سرعة القراءة مقابل سرعة الكتابة

كل Index بيسرّع القراءة (SELECT) لكن بيبطّئ الكتابة (INSERT/UPDATE/DELETE). لازم توازن! القاعدة: لو الجدول بيُقرأ أكتر ما بيُكتب عليه → استخدم Indexes. لو الكتابة أكتر → قلّل الـ Indexes.

إدارة

إدارة الـ Indexes

SQL - إدارة Indexes 
-- حذف Index
DROP INDEX idx_emp_lastname;

-- عرض كل الـ Indexes على جدول معين
SELECT index_name, column_name, index_type
FROM user_ind_columns
JOIN user_indexes USING (index_name)
WHERE table_name = 'EMPLOYEES';

-- إعادة بناء Index (لو أداؤه بقى بطيء بعد تعديلات كتير)
ALTER INDEX idx_emp_salary REBUILD;

-- تعطيل Index مؤقتاً (مثلاً قبل bulk insert)
ALTER INDEX idx_emp_salary UNUSABLE;

-- إعادة تفعيل Index
ALTER INDEX idx_emp_salary REBUILD;

💡 نصيحة: Bulk Insert

لو هتدخل بيانات كتير مرة واحدة (مثلاً ألف صف)، الأفضل:

  1. عطّل الـ Indexes (ALTER INDEX ... UNUSABLE)
  2. أدخل كل البيانات
  3. أعد بناء الـ Indexes (ALTER INDEX ... REBUILD)

كده بدل ما Oracle يحدّث الـ Index مع كل INSERT، بيبنيه مرة واحدة في الآخر!

مقارنة

Views vs Indexes - الفرق الواضح

👁️ Views

  • جدول افتراضي (Virtual)
  • مش بتخزن بيانات
  • بتبسّط الـ Queries
  • بتحسن الأمان
  • مش بتأثر على الأداء مباشرة
  • بتتكلم مع المطورين
VS

⚡ Indexes

  • Data Structure حقيقي
  • بتخزن بيانات مرتبة
  • بتسرّع البحث
  • بتبطّئ الكتابة
  • بتأثر على الأداء بشكل كبير
  • بتتكلم مع الـ Engine

جدول مقارنة:

الخاصية View Index
الهدف تبسيط + أمان سرعة البحث
تخزين بيانات ❌ لا ✅ نعم
إنشاء CREATE VIEW CREATE INDEX
بتشوفها في الـ Query؟ ✅ نعم (في FROM) ❌ لا (تلقائي)
التأثير على SELECT لا تأثير مباشر تسريع كبير
التأثير على INSERT/UPDATE لا تأثير بطء بسيط
القاعدة الذهبية: الـ View بتبسّط حياة المبرمج، والـ Index بيسرّع حياة المستخدم. هم مش بدائل لبعض - استخدمهم مع بعض!
تمارين

تمارين عملية

جرّب تحل التمارين دي عشان تتأكد إنك فاهم Views و Indexes كويس!

تمرين 1: إنشاء View بسيطة

سهل

أنشئ View اسمها it_employees بتعرض اسم الموظف (first_name, last_name) ومرتبه من جدول employees للموظفين اللي في قسم IT (department_id = 20).

استخدم CREATE VIEW ... AS SELECT ... FROM ... WHERE ...

SQL
CREATE VIEW it_employees AS
SELECT first_name, last_name, salary
FROM employees
WHERE department_id = 20;

تمرين 2: View مع حساب

سهل

أنشئ View اسمها employee_annual بتعرض employee_id, first_name, salary, والمرتب السنوي (salary * 12) باسم annual_salary.

استخدم salary * 12 AS annual_salary في الـ SELECT.

SQL
CREATE VIEW employee_annual AS
SELECT
    employee_id,
    first_name,
    salary,
    salary * 12 AS annual_salary
FROM employees;

تمرين 3: View مع JOIN

متوسط

أنشئ View اسمها emp_dept_view بتعرض اسم الموظف الكامل (first_name || ' ' || last_name باسم full_name)، اسم القسم (department_name)، والمرتب.

هتحتاج JOIN بين employees و departments على department_id.

SQL
CREATE VIEW emp_dept_view AS
SELECT
    e.first_name || ' ' || e.last_name AS full_name,
    d.department_name,
    e.salary
FROM employees e
JOIN departments d ON e.department_id = d.department_id;

تمرين 4: View مع GROUP BY

متوسط

أنشئ View اسمها dept_summary بتعرض department_name, عدد الموظفين (emp_count), متوسط المرتب (avg_salary مقرّب لأقرب عدد صحيح).

استخدم JOIN + GROUP BY + COUNT + ROUND(AVG(...))

SQL
CREATE VIEW dept_summary AS
SELECT
    d.department_name,
    COUNT(e.employee_id) AS emp_count,
    ROUND(AVG(e.salary)) AS avg_salary
FROM departments d
LEFT JOIN employees e ON d.department_id = e.department_id
GROUP BY d.department_name;

تمرين 5: View مع WITH CHECK OPTION

متوسط

أنشئ View اسمها senior_employees للموظفين اللي مرتبهم أكتر من 8000، مع WITH CHECK OPTION. بعدين جرّب تعمل UPDATE لموظف وتخلي مرتبه 5000 - إيه اللي هيحصل؟

SQL
CREATE VIEW senior_employees AS
SELECT employee_id, first_name, salary
FROM employees
WHERE salary > 8000
WITH CHECK OPTION;

-- ده هيفشل بـ ORA-01402!
-- لأن 5000 < 8000 فالصف هيختفي من الـ View
UPDATE senior_employees
SET salary = 5000
WHERE employee_id = 100;

تمرين 6: إنشاء Index بسيط

سهل

أنشئ Index على عمود phone في جدول employees. بعدين اكتب Query بتبحث بالتليفون وهتستفيد من الـ Index.

SQL
CREATE INDEX idx_emp_phone
ON employees (phone);

-- Query هتستفيد من الـ Index
SELECT first_name, last_name, email
FROM employees
WHERE phone = '01012345678';

تمرين 7: Composite Index

متوسط

أنشئ Composite Index على (department_id, hire_date) في جدول employees. بعدين اكتب 3 queries: واحدة تستخدم الـ Index، واحدة تستخدم جزء منه، وواحدة مش هتستخدمه.

SQL
CREATE INDEX idx_emp_dept_hire
ON employees (department_id, hire_date);

-- ✅ هيستخدم الـ Index كامل
SELECT * FROM employees
WHERE department_id = 10
  AND hire_date > DATE '2024-01-01';

-- ✅ هيستخدم جزء من الـ Index (العمود الأول)
SELECT * FROM employees
WHERE department_id = 10;

-- ❌ مش هيستخدم الـ Index (العمود الأول مش في الشرط)
SELECT * FROM employees
WHERE hire_date > DATE '2024-01-01';

تمرين 8: Function-Based Index

صعب

المستخدمين بيبحثوا عن الموظفين بالإيميل من غير ما يهتموا بحروف كبيرة أو صغيرة. أنشئ Index مناسب واكتب Query تستفيد منه.

استخدم UPPER() أو LOWER() في الـ Index وفي الـ Query.

SQL
-- Function-Based Index
CREATE INDEX idx_emp_email_lower
ON employees (LOWER(email));

-- Query تستفيد من الـ Index
SELECT * FROM employees
WHERE LOWER(email) = 'ahmed@company.com';

-- ❌ دي مش هتستخدم الـ Index!
SELECT * FROM employees
WHERE email = 'ahmed@company.com';

تمرين 9: تحليل - هل Index مناسب؟

صعب

عندك جدول log_entries فيه 5 مليون صف. بيتضاف عليه 50,000 صف جديد كل يوم. بيتقرأ أسبوعياً بس لعمل تقارير. هل تعمل Indexes كتير عليه؟ وليه؟

الإجابة: لا! قلّل الـ Indexes!

السبب: الجدول ده heavy write (50,000 INSERT يومياً) و light read (أسبوعياً بس). كتر الـ Indexes هيبطّئ الـ INSERT بشكل كبير. الأفضل:

  • Index واحد أو اتنين بس على الأعمدة اللي بتفلتر بيها في التقارير
  • ممكن تعطل الـ Index قبل الـ bulk insert اليومي وتعيد بناءه بعدها
  • أو تستخدم Partitioning بدل Indexes كتير

تمرين 10: سيناريو متكامل

صعب

أنت DBA جديد في شركة. طلبوا منك:

  1. أنشئ View اسمها sales_report بتجمع بيانات من employees و departments و projects (عدد الموظفين لكل قسم، عدد المشاريع، إجمالي المرتبات)
  2. أنشئ الـ Indexes المناسبة عشان الـ View تشتغل بسرعة
  3. خلي الـ View تكون READ ONLY
SQL
-- 1. الـ Indexes الأول (عشان الـ JOINs تكون سريعة)
CREATE INDEX idx_emp_dept_id ON employees (department_id);
CREATE INDEX idx_proj_dept_id ON projects (department_id);

-- 2. الـ View
CREATE VIEW sales_report AS
SELECT
    d.department_name,
    COUNT(DISTINCT e.employee_id) AS emp_count,
    COUNT(DISTINCT p.project_id) AS project_count,
    SUM(e.salary) AS total_salaries
FROM departments d
LEFT JOIN employees e ON d.department_id = e.department_id
LEFT JOIN projects p ON d.department_id = p.department_id
GROUP BY d.department_name
WITH READ ONLY;

-- استخدامها
SELECT * FROM sales_report
ORDER BY total_salaries DESC;

ملخص اللي اتعلمناه النهاردة

  • View = جدول افتراضي مبني على SELECT query
  • CREATE VIEW / CREATE OR REPLACE VIEW / DROP VIEW
  • View مع JOINs و GROUP BY بتبسّط الـ Queries المعقدة
  • WITH CHECK OPTION بتحمي من تعديلات تخفي الصف من الـ View
  • WITH READ ONLY بتمنع أي تعديل من خلال الـ View
  • Index = data structure بيسرّع البحث (B-Tree, Bitmap, Unique, Composite)
  • CREATE INDEX / DROP INDEX / ALTER INDEX REBUILD
  • Composite Index والـ Leading Column Rule
  • Function-Based Index للبحث بـ functions
  • Trade-off: سرعة القراءة مقابل سرعة الكتابة
  • Views بتتكلم مع المبرمجين، Indexes بتتكلم مع الـ Engine
